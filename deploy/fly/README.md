# Fly.io

Run these commands from the root of a **bootstrapped project**. Commit the initial
migrations generated by bootstrap before deploying. Keep `.python-version` and
`uv.lock` in source control too. Install [flyctl](https://fly.io/docs/flyctl/install/)
and run `fly auth login`.

This layout uses three apps in one organization and region:

- Application: one web Machine, one Celery worker, one Beat scheduler.
- Redis: one private Machine with an AOF-backed volume, shared by Channels and Celery.
- PostgreSQL: one private Machine with a volume, or Fly Managed Postgres instead.

The application uses the root Dockerfile without a platform-specific image.
Only `app.settings.fly` and the configuration here are Fly-specific. No nginx is
needed: Fly terminates HTTPS and proxies HTTP, WebSockets, and MCP streaming.

## Create the apps

Choose globally unique, lowercase, hyphenated app names. They need not match the
Python project name. Replace these example values:

```bash
export FLY_ORG=personal
export FLY_REGION=iad
export FLY_WEB=my-unique-project
export FLY_REDIS="${FLY_WEB}-redis"
export FLY_POSTGRES="${FLY_WEB}-postgres"

fly apps create "$FLY_WEB" --org "$FLY_ORG"
fly apps create "$FLY_REDIS" --org "$FLY_ORG"

# Hex passwords are safe to embed in connection URLs. Keep these in a password manager.
REDIS_PASSWORD=$(openssl rand -hex 32)
DJANGO_SECRET=$(openssl rand -hex 48)
printf 'REDIS_PASSWORD=%s\n' "$REDIS_PASSWORD" | fly secrets import --app "$FLY_REDIS"
fly volumes create redis_data --app "$FLY_REDIS" --region "$FLY_REGION" --size 1
fly deploy deploy/fly/redis --app "$FLY_REDIS" --primary-region "$FLY_REGION" --ha=false --no-public-ips

printf 'SECRET_KEY=%s\nREDIS_URL=redis://:%s@%s.internal:6379/0\n' \
  "$DJANGO_SECRET" "$REDIS_PASSWORD" "$FLY_REDIS" | fly secrets import --app "$FLY_WEB"
```

Redis binds IPv4 and IPv6: Fly's `.internal` DNS uses IPv6. Neither data-service
config exposes a public port. Keep these Machines running; direct `.internal`
connections do not wake stopped Machines.

## Choose PostgreSQL

### Simple singleton

```bash
fly apps create "$FLY_POSTGRES" --org "$FLY_ORG"
POSTGRES_PASSWORD=$(openssl rand -hex 32)
printf 'POSTGRES_PASSWORD=%s\n' "$POSTGRES_PASSWORD" | fly secrets import --app "$FLY_POSTGRES"
fly volumes create postgres_data --app "$FLY_POSTGRES" --region "$FLY_REGION" --size 1
fly deploy deploy/fly/postgres --app "$FLY_POSTGRES" --primary-region "$FLY_REGION" --ha=false --no-public-ips
printf 'DATABASE_URL=postgresql://appuser:%s@%s.internal:5432/app?sslmode=disable\n' \
  "$POSTGRES_PASSWORD" "$FLY_POSTGRES" | fly secrets import --app "$FLY_WEB"
```

This runs the official PostgreSQL 18 image, not the legacy `fly postgres` product.
Its volume mounts at `/var/lib/postgresql`, as required by that image. The URL
uses the organization's encrypted private network without PostgreSQL TLS.
`POSTGRES_PASSWORD` initializes a new database only; changing the secret later
also requires changing the database role's password.

### Managed Postgres

Skip creating the singleton PostgreSQL app and volume above. Instead:

```bash
fly mpg create --org "$FLY_ORG" --region "$FLY_REGION"
fly mpg list --org "$FLY_ORG"
fly mpg attach YOUR_CLUSTER_ID --app "$FLY_WEB"
```

Attaching sets `DATABASE_URL` to the pooled endpoint. Fly settings disable Django
server-side cursors for transaction pooling. From the cluster dashboard's Connect
tab, copy the **direct** connection URL into a `DATABASE_MIGRATION_URL` app secret
(use `fly secrets import --app "$FLY_WEB"` and stdin). The release command uses
that URL for migrations; web and Celery continue to use the pooled URL.
See [Fly's connection guide](https://fly.io/docs/mpg/client-configuration/).

Moving an existing singleton to Managed Postgres requires a database dump/restore
and a cutover with writes stopped. Attaching a cluster does not migrate data.

## Deploy the application

```bash
fly deploy --config deploy/fly/fly.toml --app "$FLY_WEB" --primary-region "$FLY_REGION" --ha=false
fly scale count web=1 worker=1 beat=1 --app "$FLY_WEB"
fly status --app "$FLY_WEB"
fly checks list --app "$FLY_WEB"
fly logs --app "$FLY_WEB"
```

Use the same deploy command for subsequent releases. `--ha=false` avoids spare
Machines. Keep **exactly one web and one Beat Machine**: MCP sessions currently
live in one process, and multiple schedulers would enqueue duplicate tasks.
Immediate deployment deliberately restarts these processes; expect brief downtime
and MCP/WebSocket clients to reconnect. Switch to stateless MCP or implement
session routing before scaling web. Worker count and concurrency can be adjusted
separately. A failed migration prevents the new application release; design schema
changes to remain compatible with the previous image during deployment.

The release command checks for missing migrations, then applies committed ones.
It never generates production migrations. Static files are collected when the
image builds and served by WhiteNoise. `/health/` is a lightweight liveness check;
it does not claim the database or Redis are healthy.

By default, the canonical origin is `https://<app-name>.fly.dev`, derived from
`FLY_APP_NAME`. For a custom domain, provision its Fly certificate and set
`BASE_URL=https://your-domain.example` as an app secret. This sets allowed hosts,
CSRF trust, OAuth issuer, discovery URLs, and MCP audience together. Clients must
use that canonical origin. Fly settings trust the proxy's HTTPS header; do not
expose the application port directly to the public internet.

`manage.py check --deploy` retains warnings for native OAuth loopback callbacks
and for HSTS subdomain/preload policy. HSTS is enabled for one hour on this host;
subdomain coverage and preload remain opt-in for domains you control. The OAuth
registration validator restricts HTTP callbacks to loopback addresses.

Create your first account on the web Machine:

```bash
fly ssh console --app "$FLY_WEB" --select
# Select web, then:
python manage.py createsuperuser
```

Open the public URL and `/vue/test`. Open two browser tabs and check WebSocket
broadcasts. Connect an OAuth-capable MCP client to `https://<app-name>.fly.dev/mcp`
and test login, consent, and a tool call. Check worker and Beat startup in logs.

For a **disposable test deployment only**, the existing automated protocol smoke
test can run on the web Machine against the public URL. It creates and deletes a
temporary user and OAuth client in that deployment's database:

```bash
python dev/smoke_test.py "https://${FLY_APP_NAME}.fly.dev"
```

## Operations and limits

These defaults favor simplicity: five always-running Machines with the singleton
Postgres option. Redis and self-managed Postgres each have a single disk and no
failover. Monitor disk space and memory, arrange database backups outside the app,
and test restoration. Volume snapshots alone are not a complete database backup
strategy. Managed Postgres handles database availability and backups; Redis still
needs its own recovery plan. AOF's one-second fsync can lose recent writes on a
crash. Celery tasks should tolerate retries and application deploys.

Uploaded media must use persistent object storage before enabling uploads; the
application filesystem is ephemeral. Schedule OAuth `cleartokens` cleanup and
add registration rate limiting as appropriate for a public deployment. The demo
WebSocket broadcast and dynamic OAuth client registration remain public.

For disposable tests, destroy only the named apps you created (this deletes their
volumes too): `fly apps destroy APP_NAME`. Managed Postgres clusters have a separate
lifecycle; destroy the test cluster explicitly if you created one.

Reference: [Fly app configuration](https://fly.io/docs/reference/configuration/).
